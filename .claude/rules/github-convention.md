# PR / 이슈 컨벤션

`.github/`의 템플릿은 모두 **한국어**다. PR·이슈 본문도 한국어로, 템플릿 섹션 구조를 그대로 유지해 작성한다. 섹션을 임의로 삭제하거나 순서를 바꾸지 않는다. 해당 없는 섹션은 `- 해당 없음`으로 채운다.

## 라벨 · 이모지 · 태그 (단일 기준표)

저장소 라벨 8종이 기준이다. **이모지·태그·브랜치는 모두 라벨에서 파생된다** — PR·이슈 제목 태그는 라벨명을 대문자로 대괄호에 넣은 것, 커밋 태그는 라벨명 소문자 + 콜론, 이모지는 라벨마다 고정이다.

| 라벨 | 이모지 | 제목 태그 | 커밋 태그 | 브랜치 | 용도 |
| --- | --- | --- | --- | --- | --- |
| `feat` | ✨ | `[FEAT]` | `feat:` | `feat/<이슈번호>-<브랜치 내용>` | 새로운 기능 개발 |
| `fix` | 🐞 | `[FIX]` | `fix:` | `fix/<이슈번호>-<브랜치 내용>` | 버그 수정 |
| `api` | 🔌 | `[API]` | `api:` | `api/<이슈번호>-<브랜치 내용>` | API 설계 및 구현 |
| `db` | 🗃️ | `[DB]` | `db:` | `db/<이슈번호>-<브랜치 내용>` | DB 스키마 관련 |
| `refactor` | ♻️ | `[REFACTOR]` | `refactor:` | `refactor/<이슈번호>-<브랜치 내용>` | 코드 리팩토링 |
| `test` | 🧪 | `[TEST]` | `test:` | `test/<이슈번호>-<브랜치 내용>` | 테스트 코드 |
| `docs` | 📝 | `[DOCS]` | `docs:` | `docs/<이슈번호>-<브랜치 내용>` | 문서 작업 |
| `chore` | 🔧 | `[CHORE]` | `chore:` | `chore/<이슈번호>-<브랜치 내용>` | 빌드, 설정 등 기타 작업 |

- 브랜치 이름은 `<라벨>/<이슈번호>-<브랜치 내용>` 구조다 — `feat/12-kakao-social-login`.
  - 라벨 뒤는 슬래시 하나, 그 뒤부터는 하이픈으로만 잇는다. 이슈번호와 내용 사이도 슬래시가 아니라 하이픈이다 (`feat/12/kakao-social-login` 아님).
  - 이슈번호는 숫자만 쓴다. `#`을 붙이지 않는다 (`feat/#12-...` 아님).
  - 브랜치 내용은 영문 kebab-case. 한글·공백·대문자를 쓰지 않는다.
  - 이슈 없이 분기하지 않는다. 이슈를 먼저 만들고 번호를 확인한 뒤 브랜치를 자른다.
  - 이미 머지된 `feat/initial-project-setup`, `feat/kakao-social-login`은 이슈 번호가 없는 옛 구조다. 새 규칙은 앞으로 만드는 브랜치에만 적용한다.
- 라벨·이모지·태그를 새로 만들지 않는다. 표에 없는 성격의 작업이면 가장 가까운 것을 쓰고, 정말 없으면 사용자에게 라벨 추가를 먼저 묻는다.
- 성격이 겹칠 때는 **변경의 주된 목적**을 고른다. 다만 `feat` / `api` 사이에서는 아래 "이슈" 절의 기준(엔드포인트가 생기거나 바뀌면 `api`, 그 외 기능은 `feat`)을 따른다. 엔티티 추가로 스키마가 바뀌면 `db`.
- 라벨은 PR·이슈에 **하나만** 붙이는 것을 기본으로 한다. 제목 태그도 하나다.

## PR

- 대상 브랜치는 `dev` (최종 릴리스만 `dev` → `main`).
- 제목: `<이모지>[태그] 한국어 요약 (#이슈번호)`

  ```
  ✨[FEAT] 회원가입 API 추가 (#12)
  🐞[FIX] 회원가입 시 이메일 중복 예외 처리 (#15)
  🔌[API] 스터디룸 목록 조회 API 추가 (#18)
  🗃️[DB] User 엔티티 및 users 테이블 추가 (#19)
  ♻️[REFACTOR] OAuth2 응답 파싱 로직 분리 (#20)
  🧪[TEST] UserService 단위 테스트 추가 (#21)
  📝[DOCS] API 명세에 회원 도메인 추가 (#22)
  🔧[CHORE] Bean Validation 의존성 추가 (#23)
  ```

  - 이모지와 태그는 위 기준표에서 가져오고, PR에 붙이는 라벨과 일치시킨다. 이모지와 `[` 사이에 공백을 넣지 않는다.
  - **끝에 괄호로 이슈 번호를 붙인다** — `(#12)`. 이슈가 여러 개면 쉼표로 나열한다: `(#12, #15)`.
  - 괄호 앞에 공백 하나, 번호 앞에 `#`. `[#12]`, `(12)`, `- #12` 같은 변형을 쓰지 않는다.
  - 제목에 번호를 붙였더라도 본문 4번 섹션의 `Closes #번호`는 그대로 채운다 (머지 시 이슈 자동 종료는 본문이 담당한다).
  - 연결할 이슈가 없다면 괄호를 생략한다. 다만 PR을 올릴 거라면 이슈를 먼저 만드는 것이 기본이다.
- 템플릿(`.github/PULL_REQUEST_TEMPLATE.md`) 7개 섹션:
  1. **개요** — 목적과 핵심 변경을 한두 문장으로.
  2. **변경 사항** — API / 비즈니스 로직 / DB 단위로 bullet.
  3. **테스트** — 체크박스는 **실제로 수행한 것만** 체크한다. 안 돌렸으면 비워 두고 사유를 적는다. 추가 테스트 내역도 함께.
  4. **관련 이슈** — `Closes #번호`.
  5. **변경 파일/영향 범위** — 영향 도메인 + 주요 변경 파일을 백틱 패키지 경로로.
  6. **리뷰 요청** — 리뷰어가 집중해서 볼 지점, 고민 중인 설계 선택.
  7. **주의 사항** — 배포 전 설정 변경, `.env` 키 추가, 스키마 변경 등.
- `.env.example`에 키를 추가했다면 7번에 반드시 명시한다 (다른 개발자의 로컬 실행이 깨진다).

## 커밋 메시지

형식: `<태그>: 한국어 한 줄 요약 (#이슈번호)`

```
feat: 회원가입 API 추가 (#12)
fix: 회원가입 시 이메일 중복 예외 처리 (#15)
refactor: OAuth2 응답 파싱 로직 분리 (#20)
```

- 태그는 **대괄호 없는 소문자**로 쓰고 바로 뒤에 콜론 + 공백 하나를 둔다. `[FEAT]`, `FEAT:`, `feat :` 같은 변형을 쓰지 않는다.
- 태그는 기준표의 8종(`feat` `fix` `api` `db` `refactor` `test` `docs` `chore`) 중 하나. PR 태그와 달라도 된다 — 커밋은 그 커밋이 한 일을 따른다 (기능 PR 안의 테스트 커밋은 `test:`).
- 요약은 한국어 명사형 종결로 끝낸다 (`~추가`, `~수정`, `~분리`).
- **끝에 괄호로 해당 작업의 이슈 번호를 붙인다** — `(#12)`. 괄호 앞에 공백 하나, 번호 앞에 `#`. `[#12]`, `(12)` 같은 변형을 쓰지 않는다.
  - 보통 현재 브랜치 이름(`<라벨>/<이슈번호>-...`)의 이슈번호와 같다.
  - 이슈가 여러 개면 쉼표로 나열한다: `(#12, #15)`.
  - 연결할 이슈가 없다면 괄호를 생략한다. 다만 작업을 시작할 거라면 이슈를 먼저 만드는 것이 기본이다.
- **커밋 메시지에는 이모지를 붙이지 않는다.** 이모지는 PR·이슈 제목에만 쓴다.
- 커밋은 의미 단위로 쪼갠다. "리뷰 반영", "수정" 같은 내용 없는 메시지를 쓰지 않는다.
- 머지 커밋은 GitHub 기본 형식(`Merge pull request #N from ...`)을 그대로 둔다.

## 이슈

라벨 8종에 1:1로 대응하는 템플릿이 있다. 작업 성격에 맞는 것을 골라 열면 제목 태그와 라벨이 자동으로 채워진다.

| 종류 | 템플릿 | 제목 | 라벨(자동) |
| --- | --- | --- | --- |
| 기능 | `feat_request.md` | `✨[FEAT] ...` | `feat` |
| 버그 | `fix_request.md` | `🐞[BUG] ...` | `fix` |
| API | `api_request.md` | `🔌[API] ...` | `api` |
| DB | `db_request.md` | `🗃️[DB] ...` | `db` |
| 리팩토링 | `refactor_request.md` | `♻️[REFACTOR] ...` | `refactor` |
| 테스트 | `test_request.md` | `🧪[TEST] ...` | `test` |
| 문서 | `docs_request.md` | `📝[DOCS] ...` | `docs` |
| 기타 | `chore_request.md` | `🔧[CHORE] ...` | `chore` |

### `api` vs `feat` 템플릿 선택

- **API 관련 작업 이슈는 `api_request.md`(api 템플릿)으로 만든다.** 새 엔드포인트 추가, 기존 엔드포인트의 요청/응답 스펙·URL·HTTP 메서드 변경처럼 클라이언트와의 계약이 생기거나 바뀌는 작업이 여기 해당한다.
- **API와 관련 없는 기능을 추가할 때는 `feat_request.md`(feat 템플릿)으로 만든다.** 엔드포인트가 생기거나 바뀌지 않는 작업 — 내부 도메인 로직·정책, 스케줄러/배치, 보안 설정, 공통 모듈 추가 등이 여기 해당한다.
- 판단 기준은 하나다: **이 작업으로 엔드포인트가 생기거나 스펙이 바뀌는가?** 그렇다면 `api`, 아니면 `feat`.
- api 템플릿을 골랐으면 엔드포인트·요청/응답·에러 코드 표를 반드시 채우고, 작업 후 `docs/api-spec.md`도 함께 갱신한다.

### 그 밖의 주의점

- 버그 이슈만 제목 태그가 라벨과 다르다 — 이슈는 현상을 말하므로 `[BUG]`, 그 수정 PR은 `[FIX]`다.
- 템플릿마다 고유 섹션이 있다: API는 엔드포인트·요청/응답·에러 코드 표, DB는 컬럼 변경 내역과 연관관계, 테스트는 슬라이스 선택과 검증 케이스, 문서는 대상 문서 체크리스트, 기타는 작업 종류 체크리스트와 `.env` 키 추가 여부. 해당 표/체크리스트를 비워 두지 않는다.
- 제목의 이모지와 태그를 지우지 않는다. 라벨은 템플릿 frontmatter가 자동 부여하므로 수동으로 바꾸지 않는다 (기준표에 없는 라벨을 붙이면 라벨이 새로 생성되어 목록이 오염된다).
- 모든 템플릿이 **영향 범위**(관련 도메인 + 패키지/파일 경로)와 **완료 조건(Acceptance Criteria)** 체크리스트를 요구한다. 두 섹션은 비워 두지 않는다.
- 완료 조건은 검증 가능한 문장으로 쓴다. "잘 동작한다" 대신 "존재하지 않는 ID로 조회하면 `USER404_1`이 반환된다"처럼.
- 버그 이슈는 재현 단계 → 기대 동작 → 실제 동작 순서를 채우고, 에러 메시지/스택트레이스가 있으면 그대로 붙인다.
- 리팩토링 이슈의 완료 조건에는 "기존 기능이 모두 동일하게 동작함을 확인"을 유지한다.

## 작업 흐름

1. 이슈 생성 (적절한 템플릿 — API 작업이면 api, 그 외 기능이면 feat) → 발급된 이슈 번호 확인 → `dev`에서 `<라벨>/<이슈번호>-<브랜치 내용>` 브랜치 분기.
2. 커밋 (`<태그>: 요약 (#이슈번호)`) → push → `dev`로 PR. 제목 끝에 `(#이슈번호)`, 본문 4번 섹션에 `Closes #번호`.
3. 리뷰 반영 후 머지.

커밋·push·PR 생성은 사용자가 요청할 때만 수행한다.
